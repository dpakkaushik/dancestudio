## 1. Bugs found and fixed

### 🟡 A1 · An owner could put a business on Discover having paid nothing
**Severity: critical — it is a bypass of the app's only revenue mechanism.**

`tenants` carried one permissive RLS policy, `"owners update own tenants"`, that
named **no columns**. Every write the application makes to that table goes
through a `SECURITY DEFINER` function that validates first — but PostgREST is a
door too, and a direct `PATCH /rest/v1/tenants?id=eq.…` walked past all of them.

Proven end to end by `scripts/rls-proof-tenant-columns.ps1`:

```
6.  Owner flips studio -> artist page by hand: WROTE trainer_business  -- PAID GATE BYPASSABLE
6b. ...and then lists it, having bought no plan at all: WROTE listed   -- FREE PUBLIC BUSINESS
```

The two compose. `type` is a plain text column whose CHECK allows both values,
so a PATCH turns a studio (which costs a verified organization **and** its own
₹1,200/month subscription) into an artist page (which costs the ₹700 Artist
plan) and buys neither. And `guard_tenant_visibility` gates only
`new.type = 'studio'` — so once flipped, listing it is gated by nothing at all.

Note what *did* hold, because it says exactly where the line was: About's
220-character cap and the phone's shape were **refused**, because those rules
are CHECK constraints on the column. The rules that lived only inside a function
were not. **A rule the database does not keep is a rule that holds only at the
door you went in by.**

*Fix* — `supabase/migrations/20260913100000_doors_that_were_not_doors.sql`:
drops the orphan policy (nothing in the app updates `tenants` directly — verified
by grepping every `.from("tenants")` call site: all reads), adds a
`guard_tenant_type` trigger in the shape of the existing `guard_profile_role`,
so the gate cannot silently reopen if a policy is ever added back.

### 🟡 A2 · A `javascript:` URL could be stored as a business's link — and shown to the admin reviewing it
**Severity: high — stored XSS, aimed at the account that can approve verifications.**

The same hole, different column. `socials` was constrained to "an array of at
most twelve"; the rule that each entry is an `http(s)` address lived only in
`update_tenant_profile` / `update_my_profile`. A direct PATCH stored anything:

```
3. Owner stores a javascript: link: WROTE {url=javascript:alert(1); platform=Instagram}
```

The app renders links as `href={l.url}` in three places, and the third is the
serious one:

- `features/profiles/components/PublicProfile.tsx` — the public studio/artist page
- `features/profiles/components/PublicPersonPage.tsx` — the public person page
- `features/admin/components/VerificationQueue.tsx` — **the admin's verification queue**

A business applying to be verified could put a script URL in front of the one
account able to approve it. `public.profiles.socials` had the identical gap.

*Fix*, in two independent layers:
1. **The database keeps the rule now** — `socials_are_web_links()` as a CHECK on
   both columns, using the same regex the two functions already apply, so nothing
   valid becomes invalid. Any link already stored that is not `http(s)` is
   removed by the migration (it is a live payload, not data worth keeping) and
   the count is announced.
2. ✅ **`safeHref()`** (`lib/constants/socials.ts`) at all three render sites —
   an address that is not `http(s)` is not drawn. Two guards, because the cost of
   the second is a function call and the cost of being wrong is a script running
   in someone else's session.

### ✅ A3 · A proof script had been dead, silently, for weeks
`scripts/rls-proof.ps1` — the Step 1 profiles proof — did not run at all. It
threw a **parse error**, so it was never proving anything:

```
Unexpected token 'RLS' in expression or statement.
```

Cause: the file is UTF-8 without a BOM, and **Windows PowerShell 5.1 decodes a
BOM-less `.ps1` as ANSI**. A UTF-8 em dash (`E2 80 94`) then reads as `â€"` —
and `0x94` is U+201D, a smart quote **PowerShell accepts as a string
delimiter**. The literal ended early and the file stopped parsing.

*Fix*: a UTF-8 BOM on every `.ps1` carrying a non-ASCII byte (9 files). The
proof runs and passes now. Worth knowing generally: this will silently kill any
future script that picks up an em dash.

## 2. Will the backend take the load?

The architecture is sound — RLS everywhere, definer RPCs as the doors, a
provider-neutral money ledger, idempotent webhooks. What it did **not** have was
any of the indexing or policy shaping that decides whether that architecture
answers in milliseconds or in seconds. All of the below is in
`supabase/migrations/20260913090000_load_policies_and_indexes.sql`.

### 🟡 B1 · Every RLS policy was re-evaluated once per row
**63 policy bodies** called `auth.uid()` bare. Written that way it is a function
call attached to the row filter — executed for **every row the query considers**.
Wrapped in a scalar subquery, `(select auth.uid())`, the planner hoists it into
an InitPlan and runs it **once**. Same value, same decision. This is Supabase's
own documented fix and the single largest lever on RLS cost.

The migration rewrites them **out of the catalog** rather than by re-typing 63
policies — a re-typed policy is one that can differ from the one it replaced, and
a policy that differs is a security bug. It is idempotent, and it covers the nine
`storage.objects` policies this repo wrote (Supabase's own are left alone).

### 🟡 B2 · The search box was a sequential scan on every keystroke
`search_dance_os` matches names two ways: `like 'term%'` and `like '% term%'`.
The second **cannot use a btree index** — a leading wildcard has no prefix to
seek on. Every keystroke scanned `tenants`, `crews` and `events` end to end.

*Fix*: `pg_trgm` GIN indexes on the lowered name/title of tenants, crews, events,
classes and profiles — a trigram index serves both shapes.

### 🟡 B3 · Search called a definer function four times per candidate row
The events branch called `event_host_name(e.tenant_id)` **four times in the
WHERE clause of every candidate row** — and that function reads `tenants`, then
calls `event_host_is_public()`, which reads `tenant_members` and `profiles`.
One search across ten thousand events was forty thousand of those.

*Fix*: `public_host_ids(term)` resolves the matching public hosts **once** per
search, as a set of ids, and the branch tests membership. Same rows, same
visibility rule — a host that is not public is not in the set, so its name still
cannot be used to find anything.

### 🟡 B4 · Missing indexes on the columns the app actually filters by
Added: `tenants(city, type)` and a listed-only partial; `events(city, start_date)`
for published events; `classes(status, tenant_id)`; `profiles(role)` and
`profiles(created_at)`; `subscriptions(tenant_id)` and
`subscriptions(status, current_period_end)` for the renewal clock;
`payments(created_at)`, `payments(subscription_id)`, `orders(status, created_at)`,
`refunds(created_at)`; and a partial on `webhook_events` where `processed_at is
null`, which the admin dashboard counts on every load.

### ✅ B5 · Discover silently loses a city's classes past 200 published classes
`app/(app)/discover/page.tsx` called `findPublishedClasses(supabase, 200)` — the
200 most recently created published classes **across every city** — and then
filtered by city in JavaScript. The moment the platform has more than 200
published classes nationally, a city's classes start vanishing from Discover,
and the style rail's ordering goes wrong with them. Nothing warns; the list just
gets shorter. *(Fix below in §5.)*

### 📋 B6 · The auth server is on the critical path of every request
`proxy.ts` matches everything except `_next/static`, `_next/image` and
`favicon.ico`, and calls `supabase.auth.getUser()` — a network round trip to
Supabase Auth — on each one. For a signed-in user that is one auth call **per
request**, including every public asset and the Cashfree webhook route. It is a
hard scaling ceiling and a single point of failure for all traffic.
*(Already flagged as NEXT TO DO #13. Fix below in §5.)*

### 📋 B7 · No rate limiting anywhere
There is none — not on search, not on `report_content`, `send_enquiry`,
`open_support_thread`, or sign-up. RLS decides *who* may do a thing, never *how
often*. For a public consumer app this is the main abuse surface.
**Recommended**: a `rate_limits` table plus one `rate_limit_hit(bucket, limit,
window)` definer function called from the server actions that front the risky
RPCs — additive, and it does not require touching any existing RPC body.
Not built: it wants your call on the limits.

### 📋 B8 · `nearby_tenants` is capped at 50 rows with no pagination
Fine today, a ceiling later — Discover can never show a 51st studio.

## 3. Is the database keeping the records it should?

Yes, for the app as specified — 40 tables, every one with UUID PK, audit columns,
soft delete and RLS. The money ledger in particular is better than most: orders,
payments, refunds, payouts, payout lines, a `webhook_events` ledger giving
exactly-once delivery, and `subscriptions` as one row of truth with the provider
ids beside it.

What a marketplace at the scale you are describing normally also keeps, and this
one does not:

| Missing | Why it matters here |
|---|---|
| **Reviews / ratings** | There is no `reviews` table at all. For "the Zomato of dancers" this is not a nice-to-have — ratings are the ranking signal, the trust signal and the reason to come back. Nothing else in the schema can stand in for it. |
| **Search & impression events** | Nothing records what people searched, what they saw, or what they clicked. Without it there is no relevance ranking, no "popular near you", and no way to tell a studio why it gets no bookings. |
| **A delivery log for email/SMS** | Notifications are written to `notifications`, but nothing records what was actually *sent* and whether it landed. |
| **Device / push tokens** | No table, so no push notifications. |
| **Idempotency keys on mutating endpoints** | `webhook_events` covers the provider's side well. The user's side — a double-tapped Book button — relies on per-RPC logic instead. |

These are product decisions, not bugs, so nothing here was built. Reviews is the
one I would put first by a distance.

## 4. What passed

- **`npm run typecheck`** — clean. **`npm run lint`** — clean.
- **All 27 RLS proof scripts pass** (26 did; the 27th was the dead one in A3,
  and passes now).
- The money paths read carefully: the Cashfree webhook verifies the raw-body
  HMAC before anything else, keeps an exactly-once ledger, and lands on RPCs
  that are idempotent again on the provider's payment id — so a redelivery,
  a crash between ledger and RPC, and a retry with a fresh timestamp are all
  safe. The two payload shapes are both read. I found nothing wrong with it.
